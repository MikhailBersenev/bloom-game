## 1. Исправить правила цветных ящиков

Приоритет: **P2**.

### Текущее поведение

`colored` и `cycling` получают урон, если попадание помечено как `direct`, даже когда рядом не было матча соответствующего цвета. Поэтому линия, бомба или самолётик могут уничтожить цветной ящик любого цвета.

### Требуемое поведение

- Обычный ящик получает урон от подходящего соседнего матча и от прямого попадания бустера.
- Цветной ящик получает урон только от соседнего матча своего текущего цвета.
- Меняющий цвет ящик использует то же правило, затем меняет цвет один раз после принятого хода.
- Неразрушаемый блокер не получает урон ни при каких условиях.
- За одну волну ящик теряет не более одной жизни.

### Изменения

1. Удалить обход проверки цвета через `hit.direct` для правил `colored` и `cycling`.
2. Сохранить `direct` в инфраструктуре попаданий: он нужен обычным и будущим типам элементов.
3. Проверить, что попадание бустера в цветной ящик не создаёт ложный визуальный эффект повреждения.
4. Исправить README, где сейчас описано разрешение прямого урона любому разрушаемому ящику.

### Тесты

- Матч нужного цвета рядом повреждает `colored`.
- Матч другого цвета рядом не повреждает `colored`.
- Прямая линия не повреждает `colored` другого цвета.
- Бомба и самолётик не обходят цветовое условие.
- Аналогичные проверки выполняются для `cycling`.
- `wood` по-прежнему получает прямой урон.
- `blocker` остаётся неразрушимым.
- Ящик с несколькими жизнями теряет не более одной жизни за волну.

## 2. Засчитывать цветовые цели в комбинациях радужного шара

Приоритет: **P2**.

### Текущее поведение

В комбинациях `rainbow + line`, `rainbow + bomb` и `rainbow + plane` выбранные цветные фишки сначала заменяются бустерами. К моменту применения урона движок больше не видит исходные фишки и не увеличивает счётчик `color:N`.

### Требуемое поведение

Каждая преобразованная фишка выбранного цвета должна считаться собранной ровно один раз. Созданный на её месте бустер должен активироваться и засчитываться в цели бустеров по действующим правилам.

### Изменения

1. Добавить в `ResolutionWave` коллекцию преобразованных фишек или отложенных событий сбора.
2. Перед заменой фишки сохранить её цвет и позицию.
3. При применении волны увеличить `color:N` и очки за каждую преобразованную фишку.
4. Исключить двойной учёт, если позиция одновременно присутствует в обычных попаданиях волны.
5. Не менять правила одиночного радужного шара: он продолжает собирать фишки выбранного цвета обычным удалением.

### Предпочтительная модель

Добавить метод наподобие `transformGem(index, replacement)`, который:

- проверяет, что в клетке находится фишка;
- запоминает исходную фишку для последующего сбора;
- сохраняет новый бустер в `creations` или отдельной коллекции преобразований;
- ставит новый бустер в очередь активации;
- гарантирует единичный учёт позиции.

Это позволит не смешивать подсчёт целей с логикой конкретной комбинации.

### Тесты

Для каждой комбинации проверить:

- `rainbow + line`;
- `rainbow + bomb`;
- `rainbow + plane`.

В каждом случае тест должен подтвердить:

- точное количество собранных фишек выбранного цвета;
- отсутствие двойного учёта;
- активацию всех созданных бустеров;
- корректный прогресс общей и типовой цели бустеров;
- полное завершение каскадов.

## 3. Исправить появление фишек под препятствиями

Приоритет: **P2**.

### Текущее поведение

Столбец логически делится ящиками на независимые сегменты, но новая фишка для любого сегмента получает отрицательную координату `from`. Для сегмента под ящиком это создаёт траекторию через верх поля и само препятствие.

### Требуемое поведение

- Существующие фишки падают только внутри своего свободного сегмента.
- Новые фишки верхнего сегмента появляются над верхним краем поля.
- Новые фишки закрытого сегмента появляются у верхней границы этого сегмента и не пересекают ящик.
- Ни одна визуальная траектория не проходит через неподвижный элемент.

### Изменения

1. Расширить описание `GravityMove`, чтобы оно различало координату поля и локальную точку появления в сегменте.
2. Передавать в `compactSegment` верхнюю границу сегмента.
3. Для новых фишек рассчитывать последовательные стартовые позиции относительно этой границы.
4. При необходимости добавить признак `spawn` или `clipTop`, чтобы UI мог скрывать фишку до начала анимации внутри нужного сегмента.
5. Обновить `GameAnimations.fall()` и `dropPieces()`, если одной координаты `from` недостаточно для корректного клиппинга.
6. Проверить сегменты над, между и под несколькими препятствиями.

### Важное ограничение

Простая замена отрицательного `from` на строку над сегментом может всё ещё наложить новую фишку на ящик. Модель должна явно определить точку входа и способ скрытия до появления в свободной области.

### Тесты движка

- Обычный столбец без препятствий сохраняет прежнюю гравитацию.
- Один ящик делит столбец на два независимых сегмента.
- Несколько ящиков создают несколько независимых сегментов.
- Выжившие фишки не пересекают границы сегментов.
- Для каждого нового элемента указан корректный источник появления.

### Тесты UI

- Новая фишка верхнего сегмента начинает движение над полем.
- Новая фишка нижнего сегмента не отображается поверх ящика.
- Элемент становится видимым только при входе в свободную часть сегмента.
- Существующие фишки заканчивают падение до начала отдельной фазы появления новых, если текущая последовательность сохраняется.
- Reduced motion не меняет итоговое состояние.

## 8. Ручные сценарии приёмки

1. Создать матч нужного цвета рядом с цветным ящиком — ящик теряет одну жизнь.
2. Создать матч другого цвета — ящик не изменяется.
3. Направить линию или бомбу через цветной ящик без подходящего матча — ящик не повреждается.
4. Выполнить каждую комбинацию радужного шара с другим бустером — цветовая цель увеличивается на число преобразованных фишек.
5. Запустить цепочку созданных бустеров — каждая активация учитывается один раз.
6. Удалить фишки под ящиком — новые элементы появляются в нижнем сегменте без прохождения через препятствие.
7. Проверить столбец с несколькими ящиками и пустотами в разных сегментах.
8. Проверить победу на последнем ходу после rainbow-комбинации.
9. Проверить повтор уровня после поражения и переход после победы.
10. Повторить визуальную проверку с включённым reduced motion.

## 9. Критерии готовности

Исправления считаются завершёнными, когда:

- поведение цветных ящиков соответствует ТЗ;
- прямой бустерный удар не обходит цветовое условие;
- все преобразованные радужным шаром фишки учитываются в цветовых целях ровно один раз;
- фишки не проходят через ящики при появлении и падении;
- все новые регрессионные тесты проходят;
- полный существующий набор тестов остаётся зелёным;
- сборка и проверка форматирования проходят;
- README соответствует фактическому поведению;
- значимые комментарии игровой логики написаны на русском языке.

## 10. Риски

- Изменение правил цветных ящиков может повлиять на баланс и проходимость существующих уровней. После исправления следует прогнать симуляции и вручную проверить уровни с большим количеством `colored` и `cycling`.
- Учёт преобразованных фишек изменит регрессионные хеши поведения. Их можно обновлять только после проверки, что изменение ожидаемо и ограничено нужными счётчиками и очками.
- Новая модель траекторий затрагивает контракт между движком и UI. Нужно одновременно обновить типы, engine-тесты и presentation-тесты.
- Последовательность случайных чисел не должна измениться без необходимости, иначе детерминированные сценарии и баланс уровней могут измениться шире запланированного.
