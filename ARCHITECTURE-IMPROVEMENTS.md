# Предложения по улучшению архитектуры Bloom Match-3

## Контекст

Проект уже построен вокруг удачного разделения игрового движка и пользовательского интерфейса:

- `src/core/`, `src/boosters/`, `src/entities/` и `src/goals/` содержат состояние и правила игры;
- `src/ui/` отвечает за ввод, DOM, анимации и звук;
- движок не зависит от DOM и получает визуальный обработчик через callback `animate`;
- уровни описываются декларативными конфигурациями;
- поведение расширяется через реестры правил и отдельные реализации бустеров.

Исследование выполнено с сопоставлением к каталогу паттернов [Refactoring.Guru](https://refactoring.guru/ru/design-patterns/catalog).

Главный вывод: проект уже использует несколько паттернов по назначению. Улучшения должны усиливать существующие границы, а не добавлять классы ради формального соответствия каталогу.

## Текущие архитектурные соответствия

### Facade — сильное соответствие

`Game` предоставляет простой интерфейс к подсистемам поля, поиска матчей, gravity, целей и разрешения хода.

- Файл: [`src/core/Game.js`](src/core/Game.js)
- Рекомендации Refactoring.Guru: [Facade](https://refactoring.guru/ru/design-patterns/facade)

Сохранять этот подход. Не следует давать UI прямой доступ к внутренним алгоритмам `ResolutionWave`, `Gravity` или `MoveResolver`.

### Prototype — сильное соответствие

`cloneElement()` рекурсивно копирует игровые элементы и вложенное содержимое ящиков, назначая новые runtime-ID.

- Файл: [`src/entities/Piece.js`](src/entities/Piece.js)
- Рекомендации Refactoring.Guru: [Prototype](https://refactoring.guru/ru/design-patterns/prototype)

Сохранять клонирование как механизм создания runtime-экземпляров из конфигураций уровней.

### Strategy — сильное соответствие

Стратегии реализованы через:

- отдельные классы бустеров;
- `elementRules` для типов препятствий;
- внедряемые `random` и `animate`.

- Файлы: [`src/core/ResolutionWave.js`](src/core/ResolutionWave.js), [`src/entities/obstacles/rules.js`](src/entities/obstacles/rules.js)
- Рекомендации Refactoring.Guru: [Strategy](https://refactoring.guru/ru/design-patterns/strategy)

Это наиболее удобная точка расширения проекта.

### Adapter — сильное соответствие

`GameAnimations` преобразует события движка (`swap`, `remove`, `fall`, `ready`) в DOM-анимации и звуковые эффекты.

- Файл: [`src/ui/animations.js`](src/ui/animations.js)
- Рекомендации Refactoring.Guru: [Adapter](https://refactoring.guru/ru/design-patterns/adapter)

Движок не должен получать зависимости от конкретной реализации этого адаптера.

### Bridge — частичное архитектурное соответствие

Engine и UI развиваются независимо через callback событий. Это похоже на Bridge, но реализовано функционально, без отдельных иерархий абстракций и реализаций.

- Документация границ слоёв: [`CODEBASE-DESCRIPTION.md`](CODEBASE-DESCRIPTION.md)
- Рекомендации Refactoring.Guru: [Bridge](https://refactoring.guru/ru/design-patterns/bridge)

Текущая реализация достаточна для браузерной игры и не требует формального усложнения.

## Приоритетные улучшения

### P1. Заменить `switch` комбинаций бустеров на реестр стратегий

Сейчас [`BoosterCombinationResolver`](src/boosters/BoosterCombinationResolver.js) содержит `switch` по комбинациям (`rainbow+rainbow`, `bomb+bomb`, `line+plane` и т. д.). При добавлении нового типа бустера необходимо изменять центральный класс.

Предлагается выделить единый реестр обработчиков:

```js
const combinationStrategies = new Map([
  ['bomb+bomb', (context) => resolveBombBomb(context)],
  ['line+line', (context) => resolveLineLine(context)],
  ['rainbow+rainbow', (context) => resolveRainbowRainbow(context)],
]);
```

Целевой поток:

1. Нормализовать пару типов в стабильный ключ.
2. Получить обработчик из реестра.
3. Передать ему контекст `wave`, позиции и элементы.
4. Вернуть понятную ошибку или безопасно проигнорировать неизвестную комбинацию.

Преимущества:

- меньше условной логики в `BoosterCombinationResolver`;
- проще тестировать каждую комбинацию отдельно;
- добавление комбинации не затрагивает общий алгоритм разрешения волны;
- лучшее соответствие Strategy и Open/Closed Principle.

Важно: не нужно создавать отдельный класс для каждой комбинации, пока обработчики остаются короткими и не имеют собственного состояния. Простых функций-стратегий будет достаточно.

### P1. Формализовать контракт событий движка

Сейчас событие формируется в [`Game.emit`](src/core/Game.js) и передаётся в `animate(event, game)`. Это рабочее решение, но структура событий не закреплена единым контрактом.

Предлагается:

- описать типы событий в `src/types.js`;
- разделить общие поля и поля конкретных событий;
- запретить UI изменять event snapshot;
- документировать жизненный цикл: `swap → remove → fall → cascade → ready`;
- добавить проверку неизвестных типов событий в тестах.

Пример концептуальной структуры:

```js
/**
 * @typedef {{ type: 'swap', board: Cell[] }} SwapEvent
 * @typedef {{ type: 'remove', board: Cell[], removed: number[], damaged: number[] }} RemoveEvent
 * @typedef {{ type: 'fall', board: Cell[], falls: Fall[] }} FallEvent
 */
```

Это усилит Adapter-границу и упростит создание альтернативного renderer, replay или диагностического логгера.

### P1. Разделить игровые команды и их выполнение, если появятся replay или undo

Сейчас `swap()` и `activate()` являются методами фасада, а `lastCommand` хранит только последнюю запись о результате.

Если проекту понадобятся replay, undo/redo, сетевой режим или детальная телеметрия, следует ввести команды:

```js
{ type: 'swap', first: 10, second: 11 }
{ type: 'activate', index: 42 }
```

Команда должна содержать только входные данные, а `Game` — выполнять её через единый исполнитель. Для детерминированного replay нужно также сохранять seed или последовательность случайных значений.

До появления этих требований отдельные классы `SwapCommand` и `ActivateCommand` будут избыточны.

Связанный паттерн: [Command](https://refactoring.guru/ru/design-patterns/command).

### P2. Инкапсулировать генерацию runtime-ID

Сейчас счётчик идентификаторов находится в модуле [`src/entities/Piece.js`](src/entities/Piece.js). Это удобно, но делает генерацию глобальной для всего JavaScript runtime.

Рекомендуется передавать генератор ID в контекст игровой сессии или выделить небольшой `IdFactory`:

```js
class IdFactory {
  #next = 0;

  next() {
    return ++this.#next;
  }
}
```

Преимущества:

- изолированные ID между тестовыми сессиями;
- более предсказуемый replay;
- отсутствие скрытого глобального состояния;
- возможность использовать UUID или другой формат без изменения всех фабрик.

Это улучшение следует делать только если появятся требования к сериализации, нескольким игровым сессиям или воспроизводимости.

### P2. Разделить snapshot состояния и Memento-восстановление

`Game.getSnapshot()` уже создаёт глубокую замороженную копию состояния. Это полезный read-only snapshot, но не полноценный Memento: восстановление состояния отсутствует.

Если понадобится:

- отмена последнего хода;
- отладочная перемотка;
- сохранение игры;
- replay с контрольными точками;

можно добавить отдельный API:

```js
const checkpoint = game.createCheckpoint();
game.restoreCheckpoint(checkpoint);
```

Не следует добавлять `restore` только ради соответствия паттерну. Без реального сценария использования snapshot лучше оставить простым read-only API.

Связанный паттерн: [Memento](https://refactoring.guru/ru/design-patterns/memento).

### P2. При росте числа состояний выделить State-объекты

Сейчас состояние игры выражается полями `status` и `busy`, а проверки находятся в `MoveResolver` и `GameController`.

Это нормально для трёх состояний (`playing`, `won`, `lost`). При появлении новых режимов, например:

- `paused`;
- `resolving`;
- `restarting`;
- `waitingForInput`;
- `replay`;

условия начнут распространяться по нескольким модулям. Тогда можно выделить состояния с единым контрактом команд.

До этого момента достаточно оставить текущую модель и добавить тесты переходов состояний.

Связанный паттерн: [State](https://refactoring.guru/ru/design-patterns/state).

## Улучшения средней важности

### Унифицировать фабрики игровых элементов

`gem()`, `booster()` и `box()` уже являются простыми фабриками. Их можно собрать под единым API `PieceFactory`, если появятся:

- разные наборы игровых элементов;
- специальные режимы уровней;
- тестовые фабрики;
- серверная или редакторская генерация уровней.

Пока текущие функции проще и понятнее полноценной фабричной иерархии. Не следует превращать их в Abstract Factory без нескольких совместимых семейств объектов.

### Расширить событийную модель до нескольких подписчиков при необходимости

Сейчас у игры один callback визуализации. Если появятся аудио, аналитика, replay и debug-инструменты, передача всего через один callback начнёт перегружать адаптер.

Тогда можно использовать лёгкий Observer API:

```js
game.on('remove', renderer.handleRemove);
game.on('remove', analytics.handleRemove);
game.on('remove', replay.handleRemove);
```

Не следует вводить полноценную шину событий заранее: один renderer пока не создаёт такой необходимости.

Связанный паттерн: [Observer](https://refactoring.guru/ru/design-patterns/observer).

### Сохранить правила препятствий как registry/Strategy

`elementRules` — удачная часть архитектуры. Новые типы препятствий добавляются через `registerElement`, а общий алгоритм разрешения не знает деталей каждого типа.

Рекомендуется дополнительно:

- проверять наличие обязательного `canDamage` при регистрации;
- валидировать неизвестные типы на загрузке уровня;
- покрыть каждую стратегию отдельными тестами;
- не переносить правила обратно в `ResolutionWave`.

## Что не стоит добавлять сейчас

Следующие паттерны не дают заметной пользы текущему проекту:

- Singleton — глобальное состояние ухудшит тестируемость;
- Decorator — нет нескольких взаимозаменяемых слоёв поведения вокруг одного объекта;
- Proxy — отсутствует необходимость контролировать доступ к удалённому или тяжёлому объекту;
- Flyweight — игровые элементы имеют уникальные runtime-ID и изменяемое состояние;
- Visitor — набор операций над элементами пока невелик и хорошо выражен обычной доменной логикой;
- Chain of Responsibility — очередь активации бустеров не является цепочкой обработчиков, а представляет собой рабочую очередь;
- Template Method — нет устойчивой иерархии алгоритмов с общей последовательностью шагов.

## Рекомендуемый порядок работ

1. Зафиксировать типы доменных событий в `src/types.js`.
2. Заменить `switch` комбинаций бустеров на реестр стратегий.
3. Добавить тесты на регистрацию новой комбинации и неизвестные типы.
4. Сохранить текущую границу engine/UI и не допускать DOM-зависимостей в `src/core/`.
5. Вводить Command, Observer, Memento или State только при появлении соответствующего продуктового требования.
6. При необходимости replay или нескольких параллельных сессий инкапсулировать генератор ID и случайность.

## Критерии готовности улучшений

- добавление нового бустера не требует изменения общего цикла `ResolutionWave`;
- неизвестная комбинация обрабатывается предсказуемо;
- все доменные события имеют проверяемые структуры;
- engine продолжает запускаться без DOM;
- UI остаётся единственным потребителем деталей Web Animations API;
- `npm test` проходит без изменений в поведенческих хешах существующей игры;
- новые архитектурные тесты проверяют границы, а не конкретную реализацию классов.

## Итог

Проект уже находится в хорошем состоянии с точки зрения архитектурных границ. Основной практический резерв — не добавление новых паттернов, а уменьшение центральной условной логики в комбинациях бустеров и формализация событийного контракта между движком и UI.

Остальные паттерны следует вводить только тогда, когда появятся реальные требования к replay, undo, нескольким renderer-ам, сохранению состояния или дополнительным игровым режимам.
